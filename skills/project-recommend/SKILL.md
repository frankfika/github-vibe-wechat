# Project Recommend → Multi-Platform（第三方项目 → 多平台推荐）

创作者平台的**推荐项目渠道**。写独立推荐，不是项目公告，也不是作者回顾。构建交 `content-engine`（wechat-silicon-editor）。

> **共享资源位置**：`config/creator.yaml` 与 `references/`（platforms/editorial-guide）来自 **creator-platform 技能根**（安装后 `~/.agents/skills/creator-platform/`，仓库内为 `github-vibe-wechat/` 根目录）。找不到就用 glob 搜索。

## 保护身份边界（铁律）

把仓库所有者和贡献者当作第三方，除非用户明确说明另有关系。

- ❌ 绝不暗示用户制作、发布、维护或代表该项目。
- ❌ 绝不写"我做了""我们发布了""我的项目"等所有权表述。
- ✅ 第一人称观察可以："最近看到""我比较喜欢""我不会把它推荐成……"。
- 仓库声称未独立核实的，归属给项目方（"该项目称……"）。
- 不替维护者承诺支持、路线图、稳定性或商业适用性。

保持独立于自有项目系列：不用 `Vibe Coding｜` 系列标签（除非用户明确要求）；用独立自然标题，如：
- `推荐一个把小说变成 AI 短剧的开源工作台：Toonflow`
- `这个开源工具，把零散的 AI 视频步骤串成了一条工作流`

## 核验仓库

写前读当前仓库：README 与链接文档；默认分支、最新提交、当前 release、支持平台；许可证与分离的前后端仓库；官方截图、demo 媒体、安装要求；模型 API、付费服务、硬件、签名或部署前置。不稳定事实回 GitHub 或其他一手来源核验。只有当前许可证与仓库支持"开源/免费/生产可用/可自托管/可商用"等措辞时才用。README 中的性能/成本/省时数字按"项目声称"处理，除非独立复现。

## 写推荐

一条清晰的论点：为什么有用、边界在哪。阅读流：实际问题与如何注意到它 → 用具体类比解释 + 主要差异点 → 少数几个让读者理解怎么用的工作流（每个：做什么、谁受益、为什么重要）→ 真实的设置/API/成本/平台/维护要求 → 谁适合、谁可能觉得太重 → 项目地址结尾。

语气：轻松直接的中文、长短句交错、略带观点的观察者视角。避免功能清单、startup-deck 语言、泛泛行业分析、只重复开头的结尾。

保持中立：不要求读者 Star/关注/入群/购买/注册/联系维护者；不当项目推广者或社区管理员；Star/fork 数可作带日期的客观信号，但绝不变成行动号召；默认以 `项目地址：<repository URL>` 中性收尾。

## 图片与多平台

- 真实仓库/产品/官方来源图，按阅读顺序：仓库截图 → 产品主页/定位 → 每个重要工作流一张 → 可选的管理/自定义/部署图。禁止装饰性 AI 图、假仪表盘、填充图。`01_` 命名 + `图 01｜… 图片来源：…`。
- 默认交付可以是全平台包（用户说"全平台/所有链接"时必做）：X（痛点开场短帖，绝不暗示用户制作）、Reddit（一个直接相关社区 + 披露是推荐 + 读规则 + 不复制相同推广文案）、HN（中立讨论框架，不要求投票）、知乎/CSDN（保留来源、设置要求、限制、许可证）、Product Hunt（仅当用户有授权提交时给中性工作表，不写作者口吻）、B站（标题/简介/口播提纲/置顶评论/标签/真实截图，用户手动上传）、小红书（短标题、图先文后、互动问题、5–8 标签，避免"爆款"承诺）。适配细节见 `references/platforms.md`。

## 构建、校验与交付

- 单一 `h1`；默认 eyebrow `OPEN SOURCE / PROJECT NOTES`；`--strict-editorial`；本地编号图 + 完整来源图注；交付 Markdown、HTML 预览、图片目录、ZIP；需要时全平台发布页。
- 改标题/文案后重建所有产物；核对标题、许可措辞、图片路径、复制按钮、仓库 URL。
- 用户纠正所有权口吻/系列标签/标题/CTA 时，把它当作该文章的持久规则，更新所有产物与存档。
- 交付并提醒：打开 HTML → `复制公众号正文` → 粘贴到公众号；平台发布由用户执行。
